# LSA Command webchat embed: unencoded `+` in phone param — likely affects every client, not just Champion Pools

**Source:** Fwd from Maerie Yu (Sky Media Ventures) → alex@diyai.ai, cc ryan@diyai.ai, "Fwd: Sky Media Ventures LLC | Champion pools' AI Webchat," Aug 5, 2026. Original diagnosis by Juan Marcos Pante (Search Prestige), who was debugging why Champion Pools' chat widget rendered as an empty box.
**Status:** Unconfirmed against the actual LSA Command codebase — this doc is a bug report + audit checklist, not a verified fix. Someone with repo access needs to confirm before shipping anything.

## The bug

The embed code LSA Command hands out looks like this (pulled from the Champion Pools thread, July 24):

```html
<iframe id="acc-lsa-widget"
  src="https://app.lsacommand.com/chat?u=...&p=+15617255560">
</iframe>
```

The phone number is passed as `p=+15617255560` with a literal `+`. In a URL query string, `+` is the standard encoding for a space — browsers and most server-side query parsers will decode `p=+15617255560` as `p=" 15617255560"` (leading space, no plus), not `p="+15617255560"`. The `+` needs to be percent-encoded as `%2B`, or the whole value needs to go through `encodeURIComponent()`.

Juan's exact words (unrelated to the rendering bug he was actually fixing, but flagged in passing): *"the embed URL passes the phone as p=+1561..., and a plus sign in a URL reads as a space. It should be %2B."*

## Why this matters beyond one client

This wasn't caught by LSA Command — it was caught by a partner agency's dev, debugging a different problem, in passing. That means:

- It's very likely present in **every** embed generated by whatever tool/script produces this `src=` URL, not just Champion Pools'.
- Nobody flagged it as an open issue — Ryan/Alex weren't cc'd on it as a bug report, it rode in as a footnote in a thread about something else. It may not be on anyone's radar right now.
- Depending on what `app.lsacommand.com/chat` does with `p=`, the failure mode ranges from cosmetic (a malformed number displayed somewhere) to functional (click-to-call, lead routing, or call attribution silently breaking because the number never parses as valid).

## What "genuinely advanced from here" looks like — audit checklist

This doc can't verify the runtime behavior of `app.lsacommand.com` without access to that codebase/logs, so the concrete next steps are:

1. **Find the embed-code generator.** Locate wherever LSA Command builds the `<iframe src="...&p=...">` string for a client (admin panel, onboarding script, template file). Confirm whether it does any encoding on the phone value before interpolating it.
2. **Check how `p=` is consumed server-side.** In `app.lsacommand.com`'s chat handler, log or trace what `req.query.p` (or equivalent) actually resolves to for a `+1561...` input today. If it's already being normalized/re-derived from another source (e.g., looked up by `u=` instead of trusted from `p=`), the practical impact may be small — worth ruling in or out before treating this as urgent.
3. **Pull a sample of live client embed codes** (or the DB rows that generate them) and grep for `p=+1` vs `p=%2B1` to see how many existing installs carry the bug.
4. **Fix at the source:** wrap the phone value in `encodeURIComponent()` (or explicitly replace `+` → `%2B`) in the generator, so all *newly issued* embeds are correct.
5. **Decide on backfill:** existing embeds already pasted into client sites (like Champion Pools') won't self-correct — that requires either a server-side compensating fix (decode `p` leniently, treating a leading space as `+`) or re-issuing embed codes to affected clients.
6. **Loop in Search Prestige.** Juan already has the client-side repro (championpools.com) and clearly reads embed code carefully — worth a two-line reply confirming it's being tracked, since he surfaced it for free.

## What this doc is NOT

Not a patched file, not a verified root cause, not sent to anyone. Champion Pools' widget is reportedly already live again (Juan's fix was for the plugin lazy-loading issue, a separate problem from this one) — nothing here is urgent-urgent, but it's a real, low-effort, high-leverage find: one dev's side comment on someone else's ticket may be pointing at a bug silently touching every LSA Command client with phone-based chat routing.
